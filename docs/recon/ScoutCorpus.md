## 3. Tokenization, EOS, and CE measurement status

Local facts confirmed from files: `model/tokenizer.json:3-13` adds `<|endoftext|>` at id **2047**; `model/config.json` sets `eos_token_id=2047`, `vocab_size=2048`; `model/tokenizer_config.json` sets `model_max_length=256`. The intended packing rule is therefore:

1. Tokenize each `content` string with `tokenizers.Tokenizer.from_file('model/tokenizer.json')`.
2. Append exactly one token **2047** after each document.
3. Concatenate only within a slice, then take non-overlapping T=256 windows.
4. For causal CE, feed `x=tokens[i:i+256]` and `targets=tokens[i+1:i+257]`; do not let a window cross from one slice into another.

Appending EOS is important: without it, adjacent Python files become an artificial continuation and the model is not evaluated on a document boundary. A final partial window should be dropped (or reported explicitly), rather than padded because the config has no pad token.

## 4. Deduplication/leakage and slicing recommendation

* The paper-named `transformersbook/codeparrot` card warns that approximately **70% is duplicated**.
* `codeparrot/codeparrot-clean` says it removes exact matches, but the validation schema still exposes both `copies` and `hash`; retain and inspect both rather than assuming every row is independent.
* A random row split can place files from the same repository in multiple slices. It can also split a repository's generated/vendor copies across slices, creating near leakage even where exact `hash` differs.
* The validation dataset itself is described as the train split of the validation repository (`codeparrot-clean-valid`), so use it as held-out-quality material, but do not call it a canonical paper-identical holdout.

Recommended deterministic construction:

1. Fetch rows through `/rows` and retain `repo_name`, `path`, `hash`, `copies`, `license`, and `content`.
2. Remove duplicate content by a stable content hash (the supplied `hash` is useful but should be checked for collisions/sign convention; compute a local cryptographic hash when implementing).
3. Group all rows by normalized `repo_name`; never assign one repository to more than one of the 12 slices.
4. Within each repository group, order by `(path, content_hash)`; order groups by a stable hash such as `SHA256(repo_name)`, then greedily fill slices to the target token budget (16k–64k). Permit a slice to end at a document boundary, then pack to T=256 with EOS.
5. If balancing requires splitting a very large repository, make that an explicit exception and assign all files from that repository to one slice; otherwise the cleanest policy is repo-exclusive slices.
6. Record a manifest containing slice id, row ids, repo names, paths, hashes, token count, and license values. Check intersections of repo names and content hashes across all slice manifests; both intersections must be empty.

This gives 1 discovery slice + 10 held-out slices + 1 robust/null-cone slice without the severe same-repository leakage risk of contiguous row offsets.
