- Direct dependencies (`Cargo.toml:10-17`): `clap = { version = "4", features = ["derive"] }`, `ndarray = "0.16"`, `serde` with derive, `serde_json`, `anyhow`, and `memmap2`. There is no `rayon`, `thiserror`, `npy`/`ndarray-npy`, `safetensors`, `bitvec`, or equivalent bitset crate in the manifest. `Cargo.lock` confirms clap 4.6.0, ndarray 0.16.1, anyhow 1.0.102, memmap2 0.9.10 (lock-file observations, not required API constraints).
- It uses clap derive, not a builder API: `src/main.rs:21-27` has `#[derive(Parser)]`, `#[command(...)]`, a `Cli` struct with `#[command(subcommand)]`, and `src/main.rs:30` onward has `#[derive(Subcommand)] enum Commands`.

The visible command set includes `Decompile`, `Verify`, `Stats`, `Layers`, `Extract`, `Trace`, `Compare`, `Taxonomy`, `Diagnose`, `Slice`, `Xray`, `Evolve`, `Diff`, `Patch`, `MakeTestGguf`, and `Intmap` (`main.rs:30-280`). `MakeTestGguf` overrides its spelling with `#[command(name = "make-test-gguf")]` (`main.rs` near the final variant).

## 2. Reuse assessment for the requested standalone predicate synthesizer

### Directly useful

- **CLI pattern from `main.rs`**: copy the `Cli`/`Commands` derive shape and `PathBuf` argument style, but write a much smaller command enum. It is conventional and low-risk (`main.rs:21-~280`). Do not copy the large dispatch body; it is tightly coupled to this crate's model formats.
- **Emission mechanics from `emit.rs`**: the useful pieces are the small private formatters near the top: `fmt_val(v: f64)`, `is_significant(v: f64)`, and the repeated `Vec<String>` + `lines.join("\\n") + "\\n"` pattern (`emit.rs:1-~20`, and repeated throughout). The transformer Python emitter starts around `emit.rs:~400` (`emit_transformer_python`) and demonstrates emitting imports, helper functions, a named function, and serialized constants. For the target, retain the approach but emit a compact Python predicate function, escaped token sets, and explicit prev-token/char-class/conjunction expressions. The existing emitter does **not** model predicates or token strings, and it serializes huge dense model arrays, so copy patterns/functions—not the module wholesale.
- **Error style from `verify.rs`/`gguf.rs`**: use `anyhow::{Context, Result}` and add path/format context. `verify.rs:1-5` imports `Context, Result`; `load_test_cases` (`verify.rs:~35-40`) wraps `read_to_string` with a path-bearing context and JSON parse with a second context. `gguf.rs:1` imports `bail, Context, Result` and consistently validates bounds/format errors with `bail!`. This is a good convention for file/array loading.
- **`gguf.rs`'s byte-level discipline is adaptable only in spirit**: `Cursor::read_bytes` and typed little-endian readers (`gguf.rs:~215-280`) show checked parsing; `GgufFile::open` and `extract_f32` (`gguf.rs:~350-~500`) use mmap and validate EOF/type information. That does not read NPY or safetensors, and the new corpus is likely better served by a simple checked raw-f32 loader plus an NPY parser/dependency. Do not depend on the GGUF types.

### Not useful for the target's core

- **No corpus/metric/synthesis implementation exists.** `verify.rs` only defines JSON `TestCase`/`TransformerTest` structs and runs model forward passes (`verify.rs:7-~110`); it has no token-id corpus loader, per-token CE/KL arrays, NPY parsing, raw-f32 shape metadata, ablation scoring, bitset operations, or predicate enumeration.
- **No bitsets and no parallelism.** Across the inspected manifest and requested source files there is no bitset representation and no rayon usage. Existing loops are ordinary serial loops. `taxonomy.rs` uses nested pair loops and a `Vec<Vec<bool>>` adjacency matrix plus DFS (`taxonomy.rs:~45-~160`), which is not a packed row bitset and is not a useful performance basis for millions of corpus positions.
- **`slice.rs` is model-neuron slicing, not predicate slicing.** It imports `ndarray::Array2` (`slice.rs:1-6`), traces RNNs, finds active/reachable neurons (`slice.rs:~22-~84`), and rebuilds pruned matrices (`slice.rs:~90-~150`). Its `slice_transformer` later identifies active heads and dead FFN neurons from transformer traces (`slice.rs:~210-~330`). Nothing transfers to token-position bitset scoring except the general idea of precomputing boolean activity masks.
- **`trace.rs` is forward execution tracing.** `trace_quantized`/`trace_raw` allocate and record per-step vectors and logits (`trace.rs:~1-~125`), while `trace_transformer` records layer hidden states, attention patterns, and FFN activations (`trace.rs:~240+`). It does not accept externally supplied CE/KL arrays or compute conditional-zero recovery/inverse scores.
- **`xray.rs` is orchestration around the model-specific modules.** `run_xray` calls quantization, slicing, verification, tracing, and `emit_python` (`xray.rs:~145-~245`); its `decompose_weight` helper (`xray.rs:~75-~105`) is about integer-vs-residual model weights, not predicate synthesis.
- **`taxonomy.rs` is model comparison only.** It generates binary one-hot sequences (`taxonomy.rs:~15-~35`), calls `fsm::run_fsm`, computes circuit similarities, and clusters with DFS (`taxonomy.rs:~45-~160`). No token-set, prev-token, decoded-char class, conjunction, coverage, or score logic.
- **`gguf.rs` is not an NPY/safetensors reader.** It supports GGUF header metadata and selected GGML types; `extract_f32` explicitly handles F32/F16/BF16/Q8_0/Q4_0 and rejects other types (`gguf.rs:~380-~500`). Its `memmap2` use is potentially a performance pattern for raw files, but it is not a reusable parser for the requested formats.

### Suggested new-crate data/algorithm boundary

`Corpus` should own token IDs, position/sequence boundaries, decoded token strings or precomputed char-class flags, and aligned original/ablated CE/KL values. A packed `BitVec`/`Vec<u64>` mask per primitive predicate should support `AND` for conjunctions and popcount-based coverage/score evaluation. Keep metric scoring independent from predicate AST enumeration, then make `emit.rs` consume the winning AST and token-string metadata. This separation is absent from neural-decompile and should be designed fresh.

## 3. Style conventions and tests

- **Error handling:** `anyhow::Result` at command/module boundaries, `?` propagation, `Context` for file/parse operations, and `bail!` for invalid formats/bounds (`verify.rs:1-5, ~35-40`; `gguf.rs:1, ~215-280, ~350-500`; `main.rs:~293 onward`). There is no `thiserror`-based domain error hierarchy.
- **Data style:** plain public structs with public fields and derives such as `Debug`, `Clone`, and `Deserialize`; domain result structs are returned directly (`verify.rs:7-33`; `slice.rs:8-20`; `taxonomy.rs:5-13`). Functions commonly take slices (`&[T]`) and return owned `Vec<T>`.
- **Allocation/style:** straightforward `Vec::with_capacity`, iterator collection, nested loops, and `format!`; `emit.rs` builds a line vector and joins once. The target's hot scoring path should not imitate every existing allocation: use packed words and reusable scratch buffers there.
- **Tests layout:** no Rust `#[cfg(test)]` module was present in the inspected requested files. The repository has root-level executable Python integration checks such as `test_emitted.py`, which invokes `./target/release/nd`, executes generated Python, loads JSON tests, and reports pass counts (`test_emitted.py:1-48`). There is also a separate `kani-proofs/` crate/directory for formal proofs (listed by the GitHub API), while the README documents `cargo kani` usage. Match the repository's observable style with focused Rust unit tests for parser/bitset/scoring behavior plus an end-to-end emitted-Python test; do not add a Kani layer unless the new project actually needs formal proofs.
- **Naming/output:** descriptive structs, snake_case functions, comments explaining model assumptions, and human-readable report output with `format!`; `emit.rs` emits a trailing newline consistently (`emit.rs` throughout).

## 4. Recommendation

1. **Write fresh core implementation.** Do not depend on `neural-decompile` as a crate: it is a binary-only package (`Cargo.toml:6-8`), its modules are private (`main.rs:1-19`), and the reusable-looking modules depend on private, model-specific types (`quantize`, `transformer`, `weights`, `fsm`). It has none of the target's required NPY/raw-f32/safetensors, token-string, bitset, predicate AST, CE/KL, or enumeration machinery.
2. **Copy/adapt only the CLI skeleton**: `Cli`, `Commands`, `Parser`/`Subcommand`, `PathBuf`, and `main() -> anyhow::Result<()>` pattern (`main.rs:21-~30, ~293+`). Use a smaller command surface such as `synthesize` plus optional `emit`/`score` modes.
3. **Copy/adapt the emission primitives, not full `emit.rs`**: `fmt_val`/line accumulation/trailing-newline conventions (`emit.rs:1-~20`) are useful. The existing `emit_transformer_python` (`emit.rs:~400+`) is evidence for reliable generated-Python structure, but its dense model serialization and model-specific helper code should be replaced by a predicate AST printer with identifier/string escaping and deterministic set ordering.
4. **Use `verify.rs` only as an error-handling/test-shape reference**, especially `load_test_cases` (`verify.rs:~35-40`). Its forward-pass verification routines are irrelevant because the new inputs are precomputed CE/KL arrays.
5. **Do not copy `xray.rs`, `taxonomy.rs`, `trace.rs`, or `slice.rs`** for the requested synthesizer. They all operate on RNN/transformer weights and activations (`xray.rs:~145-245`; `trace.rs:~1-125, ~240+`; `slice.rs:~22-150, ~210-330`; `taxonomy.rs:~15-160`).
6. **Do not copy `gguf.rs` except perhaps checked-reader idioms.** It is a substantial GGUF parser/dequantizer (`gguf.rs:~350-~738`) and creates irrelevant maintenance surface. Add a focused raw-f32 reader and a proper NPY reader (or a narrowly scoped maintained dependency) instead; add safetensors only if this pipeline actually needs it.
7. **Add rayon only after the representation is correct.** The source has no rayon precedent. First make primitive masks and scoring allocation-free in the inner loop; then parallelize candidate evaluation if profiling shows it is needed. Use a packed bitset implementation deliberately rather than `Vec<bool>` (the only boolean matrix observed is taxonomy's adjacency matrix, `taxonomy.rs:~115-~145`).
